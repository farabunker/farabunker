{% comment %} Shared shell for every top-level page (the landing page, Chat, Ask, Search, Document library, Ask history, Images, Queue, and every page of the settings area). Lives at the project level (templates/, registered in TEMPLATES[0]["DIRS"] in config/settings.py) rather than inside tools/rag or models/registry, because both apps' page bases (tools/rag/templates/rag/base.html, models/registry/templates/inference/base.html) extend it -- the second by way of foundation/templates/_settings.html, which is itself a thin extension of this file. Template inheritance is a Django template-loader concept only -- it creates no Python import, so `models/contracts/` purity and column-privacy (`models/contracts/` never imports `tools/` or `models/registry/`) are unaffected by this file existing or being shared. Owns the design tokens, dark-mode overrides, and the shared body/nav/button rules so a palette change lives in ONE place instead of drifting between pages -- this replaces two near-duplicate copies that used to live in the per-app base.html files. Everything stays inline / offline (no external CSS or JS), per docs/ARCHITECTURE.md. Also owns the ONE global app bar (the nav block below) so every page agrees on every destination instead of drifting into per-app copies. A page marks itself current by overriding the matching `nav_current_*` block (see landing/index.html / chat/base.html / ask.html / search.html / documents.html / history.html / queue.html / vision/base.html) with `current`; this needs no JS, just plain block overrides. A settings-area page marks nothing here -- `_settings.html` sets `nav_current_settings` ONCE for all of them and the page marks its own SIDEBAR entry instead. ONE ROW, AND ONE DOOR TO THE OPERATOR SURFACES (UI-2, superseding UI-1 decision 1). UI-1 split this bar in two: a top row of what you came to USE and a second Manage row of the operator surfaces. The split was right about the two kinds of thing and wrong about the shape -- Manage was a flat run of up to ten links with no grouping, which is a menu pretending to be a nav. So the row is gone and its contents moved into a SETTINGS AREA with a real sidebar (foundation/templates/_settings.html, foundation/settings_area.py); the bar is one row again: the brand (which is also the link home), the use-surfaces, Queue, Settings, and the account area on the right. QUEUE CAME UP, NOT INTO SETTINGS. It is activity -- what this box is doing right now -- which is a thing you WATCH, not a thing you configure; it is class R and shown to everybody, exactly as it was in the Manage row. SETTINGS RENDERS FOR EVERYONE, and it is honest for everyone: it points at `/settings/`, which forwards to the first section the viewer may open (foundation/settings_area.py). `Install guides` is ungated, so nobody is ever sent to a page that refuses them, and no per-standing gate belongs on this entry itself. AVAILABILITY = MODEL BOUND (UI-1 decision 2, unchanged). A use-surface entry renders only when the role behind it has a model bound -- `surface_available`, from models.registry.context_processors.availability, which also carries the composite rules (Ask needs the answer role AND the embedding role; Images needs the vision FEATURE as well as the generate role, because with the feature off there is no /vision/ route for a url tag to resolve at all -- Django only evaluates one inside a taken branch, so the absent route raises nothing). Bound, not reachable: a nav bar that vanished whenever a workstation slept would be a worse lie than a page that says in its own words that the model is unreachable, and every one of these pages does say exactly that. The landing page gates its entry cards on the SAME keys, so the nav and the front door can never disagree. NEITHER QUEUE NOR SETTINGS IS AVAILABILITY-GATED, and Document library and Ask history are not either. The first two are STORAGE and a RECORD -- both real with nothing bound at all -- and settings is where an operator fixes "nothing is available" FROM; gating it on availability would lock them out of the box at precisely the moment they need it. The account area is the far-right block, and it renders only when accounts are on (`identity_accounts_on`): a household box's bar ends at Settings. Signed in, it names the person (in the text colour -- a username nobody can read is not an account area) and carries "Your password" and the sign-out form; signed out, a Sign in link carrying `?next=` back to the current path, so signing in returns you where you were.
