FOUNDATION, and the reason is the same one `foundation/settings_area.py` gives for owning the assistant panel's query parameter: the chrome that needs this spans four columns, and `foundation/` is the one column all of them may depend on. A settings page under `identity/` reaching into `agents/chat/templates/` for a behaviour would be a dependency pointing the wrong way up the repository map, template loader or no template loader. WHERE THE LINE IS, since only this HALF of the component moved and the asymmetry is deliberate rather than half a job. The line is not a general ordering over the repository map -- there is no such rule, and an earlier version of this comment invented one. It is the two rules `foundation/ops/tests/test_import_law.py` actually enforces: * RULE 4 -- `identity/` imports NOTHING from `agents/`, `models/` or `tools/`. It may import `foundation/`, Django, and its own `contracts`. That rule, and only that rule, is what forced this file out of `agents/chat/templates/`: the new consumer is an `identity/` page, so `foundation/` is the only home both it and the two existing consumers can reach. * RULE 2 -- every other column may import identity's four named seams (`identity.contracts.*`, `.access`, `.request`, `.audit`) and nothing else under `identity/`. NOTHING BARS `tools/` OR `models/` FROM `agents/`, which is why `tools/rag/templates/rag/panels/documents.html` keeps including `chat/_search_checklist.html` and the markup half of this component had no reason to move. That is not a tolerated exception: `models/registry/ tools.py` imports `agents.contracts.tools` in production, registered from `models/registry/apps.py::ready()`, which is the tool contract working exactly as designed. Template includes are not Python imports and nothing enforces any of this for them (`test_import_law.py` reads Python; `test_css_ownership. py` walks the include graph only to place CSS), so for a template this is a stated rule rather than a gate.
